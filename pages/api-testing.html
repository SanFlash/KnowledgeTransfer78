Phase 01

Foundation of APIs & Web Architecture

Before you test anything, you must understand what an API is, why it exists, and how the internet fundamentally works. This phase builds the mental model that every future module rests upon.

Module 01 Introduction to APIs
What is an API?

API stands for Application Programming Interface. Think of it as a formal contract between two software systems that defines how they can communicate with each other. Just as a waiter in a restaurant takes your order to the kitchen and brings back food — without you ever seeing the kitchen — an API takes your request to a server and delivers the response back to your application.

Every time you check the weather on your phone, your app is hitting a Weather API. When you pay online, a Payment API is invoked behind the scenes. When Google Maps shows up on a third-party site, the Maps API is at work. APIs are the invisible glue of the modern digital world.

📌
Real-World Analogy
You (the client) place an order (HTTP Request) with a waiter (API). The waiter goes to the kitchen (server/backend) and returns with your food (HTTP Response). You don't need to know how the kitchen operates — the waiter abstracts all of that complexity.
Why APIs Exist — The Business Case

APIs exist because it's both inefficient and dangerous to expose entire systems. Instead, a business creates a defined interface that:

  • Exposes only the required functionality (not the entire database)
  • Enforces authentication before any data is returned
  • Allows different clients (web, mobile, IoT) to consume the same backend
  • Lets third parties integrate with your platform without accessing your code

Client-Server Architecture & Request-Response Cycle

Every API interaction follows the same fundamental pattern:

1
Client Initiates
Your browser or app sends an HTTP request to a specific URL (endpoint) with headers, optional body data, and authentication.
2
Server Receives
The web server (nginx, Apache) receives the request and routes it to the appropriate application handler.
3
Application Processes
Business logic executes — queries a database, calls another service, computes a result.
4
Response Sent
The server returns an HTTP response with a status code, headers, and a response body (usually JSON).
5
Client Renders
The client parses the response and presents data to the user, or uses it to trigger further actions.

1.4 — HTTP Basics & URL Anatomy

Every API request is an HTTP request. Understanding URLs at a granular level is fundamental.

// URL Anatomy
https://api.example.com:443/v1/users/42/orders?status=active&limit=10#results

Protocol   : https                  → secure HTTP
Host       : api.example.com        → domain name
Port       : 443                    → HTTPS default (80 for HTTP)
Path       : /v1/users/42/orders    → resource path
Path Param : 42                     → user ID embedded in path
Query Str  : status=active&limit=10 → filters / options
Fragment   : #results               → client-side anchor
🔒
HTTPS vs HTTP
HTTPS encrypts the entire request/response using TLS (Transport Layer Security). In API testing, always check that sensitive endpoints enforce HTTPS. Sending auth tokens over plain HTTP is a critical security vulnerability.
Monolithic vs Microservices Architecture

Modern APIs live in one of two architectural worlds. As a tester, understanding this context changes your testing strategy significantly.

Monolithic
All features in one deployable unit. A single API gateway. Simpler to test initially, but changes affect everything. Example: A single Java WAR file containing Auth, Orders, Payments, and Inventory.
Microservices
Each feature is its own service with its own API. Requires service-to-service testing, contract testing, and resilience testing. Example: Netflix has 700+ microservices each with independent APIs.

⚠️
Idempotency Explained
An idempotent method produces the same result no matter how many times you call it with the same input. DELETE /users/5 called 3 times: first call deletes the user, subsequent calls return 404 — but the server state is the same. POST is NOT idempotent — calling POST /orders 3 times creates 3 orders.

Rate Limiting, Throttling & Retry Strategies

Rate limiting is a server-side mechanism to prevent abuse by restricting how many requests a client can make in a given time window. As a tester, you should always validate rate limiting behavior.

// Rate Limit Response Headers
X-RateLimit-Limit:     1000      ← max requests per hour
X-RateLimit-Remaining: 45        ← requests left this window
X-RateLimit-Reset:     1699284400 ← Unix timestamp when window resets
Retry-After:           60        ← seconds to wait (with 429)
🎯
Test Scenario
Deliberately exceed the rate limit in your test suite and verify: (a) the server returns 429, (b) the Retry-After header is present, (c) the system recovers after the window resets and allows traffic again.

Common JSON Validation Checks
When testing API responses: (1) Verify required fields are present. (2) Verify data types match (string vs number). (3) Verify arrays are not unexpectedly empty. (4) Verify nested objects have correct structure. (5) Check that sensitive data (passwords, SSN) is NOT returned.

Phase 04

API Testing Fundamentals

Before writing a single line of automation code, you must master manual API testing. This is where your QA mindset is built.

Module 04 Manual API Testing
The Three Pillars of API Validation
1
Request Validation
Validate that you're sending the correct URL, headers (Content-Type, Authorization), and payload structure before even looking at the response.
2
Response Validation
Check status code, response body structure (schema), data values, response headers, and response time (should be under SLA, e.g. 500ms).
3
Business Logic Validation
Verify the API enforces business rules. E.g., an order API should not allow placing an order for out-of-stock items, or for quantities exceeding warehouse capacity.
Test Design Techniques
TechniqueDescriptionAPI Example
Positive TestingValid inputs, expect successPOST /login with correct credentials → 200
Negative TestingInvalid inputs, expect errorsPOST /login with wrong password → 401
Boundary TestingEdge values at min/maxOrder quantity: 0, 1, 999, 1000, 1001
Error HandlingMalformed inputSend string where integer expected → 400/422

Critical API Test Scenarios
  • No auth token sent (expect 401)
  • Expired JWT token (expect 401)
  • Token for different user (expect 403)
  • Missing required field in body (expect 400/422)
  • Wrong data type (string → integer field)
  • Empty string where value required
  • Duplicate creation (POST same record twice)
  • SQL injection in parameters
  • XSS payload in string fields
  • Very large payloads (memory/timeout testing)
  • Accessing other user's resource by ID guessing
  • Delete already-deleted resource (expect 404)
Practical Example — Full Order API Test Checklist
Test Scenario: POST /api/orders

✅  Valid order with all required fields → 201 Created, order ID returned
✅  Missing "productId" field → 400 Bad Request, descriptive error message
✅  quantity: 0 → 422 Unprocessable Entity (business rule)
✅  No Authorization header → 401 Unauthorized
✅  Customer's token placing order for another customer → 403 Forbidden
✅  Product out of stock → 409 Conflict or custom 422
✅  Order created → verify in database that record was actually inserted
✅  Response time should be < 500ms

Postman Complete Mastery

Postman is the industry's most widely used API testing tool. Complete mastery here is non-negotiable for any API QA engineer.

Module 05 Postman End-to-End
Collections, Environments & Variables

A Collection is an organized folder of API requests. An Environment stores variables (like base URLs or tokens) that change between dev/staging/prod. Variables prevent duplication and enable dynamic testing.

// Postman Variable Scopes (highest to lowest priority)
Global     → available in all collections and environments
Collection → scoped to one collection
Environment→ set per environment (dev / staging / prod)
Local      → set within a single pre-request or test script
Data       → provided by CSV/JSON in Collection Runner

// Usage in request URL:
{{baseUrl}}/api/users/{{userId}}

// Setting a variable in a test script:
pm.environment.set("authToken", pm.response.json().token);
Pre-Request Scripts & Test Scripts (JavaScript)

Postman uses JavaScript for scripting. Pre-request scripts run before the request (set up dynamic data), test scripts run after (validate response).

// Pre-Request Script — Generate dynamic timestamp
const timestamp = new Date().getTime();
pm.environment.set("uniqueEmail", `test_${timestamp}@test.com`);
pm.environment.set("requestTime", timestamp);
// Test Script — Assertions after response
// 1. Check status code
pm.test("Status is 200", () => {
  pm.response.to.have.status(200);
});

// 2. Response time under 500ms
pm.test("Response time OK", () => {
  pm.expect(pm.response.responseTime).to.be.below(500);
});

// 3. Body contains expected fields
const body = pm.response.json();
pm.test("User has id and name", () => {
  pm.expect(body).to.have.property("id");
  pm.expect(body.name).to.be.a("string");
});

// 4. Save token for next request
pm.environment.set("token", body.accessToken);
Chaining Requests — The Login → CRUD Workflow

Real-world API testing requires chaining — using the output of one request as input to the next. This mirrors actual user workflows.

1
POST /auth/login
Send credentials. Extract access_token and user_id into environment variables.
2
GET /users/{{user_id}}
Use the token in Authorization header. Verify user profile returned matches login.
3
POST /orders
Create an order using the authenticated token. Save the returned order_id.
4
GET /orders/{{order_id}}
Fetch the order we just created and verify all fields match what was sent.
5
DELETE /orders/{{order_id}}
Clean up test data. Verify 204. Then GET the deleted order and confirm 404.
Newman CLI — Running Postman from Terminal

Newman is Postman's command-line runner. It lets you run entire collections in CI/CD pipelines without opening the Postman GUI.

Phase 06

REST API Testing

REST is not just a protocol — it's an architectural style with specific constraints. Understanding these constraints helps you validate whether an API truly behaves as a REST API should.

Module 06 REST API Architecture & Principles
The 6 REST Constraints
1
Statelessness
Each request must contain all the information needed to process it. The server stores NO session state. This means every request must include the auth token — the server can't remember you from the previous request.
2
Uniform Interface
Resources are identified by URIs. Manipulation through representations. Self-descriptive messages. HATEOAS (links to related actions in response).
3
Client-Server Separation
Client and server evolve independently. The client doesn't know how data is stored; the server doesn't know how data is displayed.
4
Cacheability
Responses must define themselves as cacheable or non-cacheable via headers (Cache-Control, ETag). Caching reduces server load and improves performance.
5
Layered System
Client can't tell if it's talking directly to the server or through intermediaries (CDN, load balancer, API gateway). This enables scaling and security.
6
Code on Demand (optional)
Server can send executable code to client (JavaScript). Rarely used but valid REST constraint.
REST Best Practices — URL Design
// Good vs Bad REST URL Design
❌ Bad — verb in URL (not resource-oriented)
GET  /getUsers
POST /createOrder
POST /deleteProduct?id=5

✅ Good — noun-based, versioned, hierarchical
GET    /v1/users
POST   /v1/orders
DELETE /v1/products/5

✅ Relationships expressed as nested resources
GET  /v1/users/42/orders        ← orders for user 42
GET  /v1/orders/99/items        ← items in order 99

✅ Filtering, sorting, pagination via query params
GET  /v1/products?category=shoes&sort=price&page=2&limit=20

Phase 07

Authentication & Authorization

Security is the most critical dimension of API testing. Understanding auth mechanisms and knowing how to test them is what separates junior testers from senior SDETs.

Module 07 API Security Basics
Authentication vs Authorization
Authentication (AuthN)
Who are you? — Verifying identity. You prove you're the right person using credentials (username/password), a token, or a certificate. Returns 401 if it fails.
Authorization (AuthZ)
What can you do? — After identity is proven, checking permissions. A valid user might not have permission to access admin endpoints. Returns 403 if it fails.
JWT (JSON Web Token) — Deep Dive

JWT is the most widely used token format for API authentication. It's a compact, self-contained token that carries claims (user info, permissions) in a verifiable format.

// JWT Structure — 3 Base64URL-encoded parts separated by dots
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.      ← Header
eyJ1c2VySWQiOiI0MiIsInJvbGUiOiJhZG1pbiJ9. ← Payload
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c ← Signature

// Decoded Header:
{ "alg": "HS256", "typ": "JWT" }

// Decoded Payload (public claims):
{
  "userId": "42",
  "role": "admin",
  "iat": 1699200000,   ← issued at
  "exp": 1699286400    ← expires at
}
🔴
JWT Testing Scenarios
(1) No token → expect 401
(2) Expired token → expect 401 with "Token expired" message
(3) Tampered payload (change userId) → expect 401 (signature mismatch)
(4) Algorithm confusion (change alg to "none") → server MUST reject
(5) Admin token on regular endpoint → should work
(6) Regular token on admin endpoint → expect 403

Phase 08

Database Validation for APIs

A response saying "Order created" means nothing until you verify the database. Backend validation is the gold standard of API test completeness.

Module 08 API + Database Testing
Why Database Validation Matters

An API can return a successful 201 response but fail to persist data if there's a transaction rollback, bug in the ORM, or race condition. Never trust the API response alone. Always verify the side effect in the database.

SQL Fundamentals for Testers
// Essential SQL for API Validation
-- Verify user was created after POST /users
SELECT id, email, created_at
FROM users
WHERE email = 'test@example.com'
ORDER BY created_at DESC
LIMIT 1;

-- Verify order was stored with correct amount
SELECT o.id, o.total, o.status, u.email
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.id = 'ORD001';

-- Check audit log for GDPR compliance
SELECT * FROM audit_logs
WHERE entity_type = 'user'
  AND action = 'DELETE'
  AND created_at > NOW() - INTERVAL '5 minutes';
API → DB Validation Workflow
1
Call API
Make the API request (POST /orders with full payload).
2
Capture Response
Extract the created resource ID from the response body.
3
Query Database
Run SQL query using the captured ID to fetch the row directly from the database.
4
Compare
Assert that DB values match the API request payload and that calculated fields (totals, timestamps) are correct.
5
Clean Up
Delete the test record from the DB or use test-specific data that gets rolled back.

import pytest
import requests

BASE_URL = "https://api.example.com/v1"

def api_session(auth_token):

    session = requests.Session()

        "Authorization": f"Bearer {auth_token}",
        "Content-Type": "application/json"
    })
    yield session
    session.close()

Module 12 Rest Assured + TestNG
Rest Assured — Fluent DSL
// Java — Rest Assured Test Example
import io.restassured.RestAssured;
import static io.restassured.RestAssured.*;
import static org.hamcrest.Matchers.*;

public class UserApiTest {

    @BeforeClass
    public static void setup() {
        RestAssured.baseURI = "https://api.example.com";
        RestAssured.basePath = "/v1";
    }

    @Test
    public void testGetUser() {
        given()
            .header("Authorization", "Bearer " + getToken())
        .when()
            .get("/users/42")
        .then()
            .statusCode(200)
            .body("id", equalTo(42))
            .body("name", notNullValue())
            .time(lessThan(2000L));  // response < 2 sec
    }

    @Test
    public void testCreateUser() {
        String body = """

Phase 13

Contract Testing

In a microservices world, services change independently. Contract testing prevents one team's changes from silently breaking another team's consumers.

Module 13 API Contract Validation — OpenAPI & Pact
What is Contract Testing?

A contract is a formal agreement between a consumer (the service calling the API) and the provider (the service exposing the API) about what the API looks like: its endpoints, request structures, response schemas, and status codes.

Without contract testing: Team A ships a new version of their User Service that renames user_id to id. Team B's Order Service (which reads user_id) breaks in production. No one noticed because each service's unit tests passed in isolation.

💡
Contract Testing vs Integration Testing
Integration tests require both services to be running simultaneously. Contract tests run independently — the consumer defines its expectations, the provider verifies it can meet them. Contract tests are faster and don't require a live environment.
OpenAPI/Swagger — API Contract as Documentation

Phase 17

API Security Testing

APIs are the #1 attack surface in modern applications. Security testing is no longer optional — it is a core QA responsibility.

Module 17 Advanced API Security — OWASP Top 10
OWASP API Security Top 10
1
Broken Object Level Authorization (BOLA)
The most common API vulnerability. User A accesses User B's data by changing an ID in the URL: GET /users/43 when logged in as user 42. Test: always check that resource IDs belong to the authenticated user.
2
Broken Authentication
Weak tokens, no rate limiting on login, accepting expired tokens. Test: try logging in 1000 times rapidly (brute force), check that expired JWTs are rejected.
3
Excessive Data Exposure
API returns more fields than the client needs (including sensitive ones like password hashes, SSNs, internal IDs). Test: analyze all response fields and flag any unexpected sensitive data.
4
Lack of Resource & Rate Limiting
No throttling on expensive operations. Test: send 1000 requests rapidly and verify 429 responses kick in.
5
Injection Attacks
SQL injection, NoSQL injection, command injection via API parameters. Test: send payloads like ' OR '1'='1, {"$where": "sleep(5000)"} in string fields.

Testing Challenges in Microservices
1
Service Dependencies
Service A calls Service B which calls Service C. A bug in C may manifest as a 500 in A. Use distributed tracing (Jaeger, Zipkin) to trace the entire request chain.
2
Asynchronous APIs
An API might return 202 Accepted immediately, but the actual work happens asynchronously via Kafka or RabbitMQ. You must poll or subscribe to verify eventual completion.

Services discover each other dynamically. In tests, ensure you're pointing at the correct service instance, not a stale registry entry.
4
Circuit Breakers
Test that circuit breakers open when a dependent service is down and that the API returns a graceful fallback response rather than hanging.

// Python — Verify Kafka event was published after API call
from kafka import KafkaConsumer
import json, requests

def test_order_publishes_kafka_event():
    # Set up consumer BEFORE calling API
    consumer = KafkaConsumer(
        'order.created',
        bootstrap_servers=['localhost:9092'],
        auto_offset_reset='latest',
        consumer_timeout_ms=5000
    )

    # Call the API
    res = requests.post('/api/orders', json={"productId": 1})
    order_id = res.json()["id"]

    # Wait for Kafka event
    events = [json.loads(msg.value) for msg in consumer]
    assert any(e['orderId'] == order_id for e in events)

Interview Preparation

Module 26 API Testing Interview Mastery
Fresher-Level Interview Questions
Q
What is the difference between PUT and PATCH?
Answer: PUT replaces the entire resource. PATCH makes a partial update. If a user has {name, email, age} and you PUT with only {name}, the email and age are erased. With PATCH, only name changes.
Q
What is the difference between 401 and 403?
Answer: 401 means "you haven't identified yourself" (no/invalid token). 403 means "I know who you are, but you're not allowed to do this" (valid token, insufficient permissions).
Q
What is API testing? Why is it better than UI testing?
Answer: API testing validates the service layer directly, without UI. It's faster (no browser rendering), more stable (APIs change less frequently than UI), catches bugs earlier in the cycle, and provides better coverage of edge cases.
Intermediate-Level Interview Questions
Q
How do you handle authentication in API automation?
Answer: I create a login fixture/utility that runs once per test session, extracts the JWT from the response, and stores it. All subsequent requests include it in the Authorization header. Token refresh logic handles expiry gracefully.
Q
What is contract testing? Why do you need it in microservices?
Answer: Contract testing verifies that a consumer and provider agree on the API interface. In microservices, teams deploy independently. Without contract tests, Team A could rename a response field and break Team B's service in production without any tests failing locally.
Q
How do you test an asynchronous API?
Answer: Poll the status endpoint until the operation completes (with a timeout), or subscribe to a WebSocket/webhook/Kafka topic and wait for the completion event. Always assert both that the initial call returns 202 and that the eventual state is correct.

"Here's the Swagger doc for a simple TODO API. In 30 minutes, write tests in Postman or your language of choice that cover: creating a TODO, listing all TODOs, updating a TODO, deleting it, and three negative test cases of your choosing."
