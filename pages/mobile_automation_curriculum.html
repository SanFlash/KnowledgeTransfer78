System Requirements & Windows Setup
OS configuration, hardware specs, and baseline tools
›
Objective

Prepare your Windows machine to host a complete mobile+web automation environment. Understand why each system setting matters and how misconfiguration causes hard-to-debug issues later.

Recommended System Specs
RAM
16 GB minimum — Android emulators alone consume 2–4 GB. Running Chrome + Node + emulator simultaneously needs headroom.
Storage
50 GB free minimum — Android Studio SDK + emulator images + node_modules can reach 30 GB.
CPU
Intel i5/i7 or AMD Ryzen 5/7 with hardware virtualization (VT-x/AMD-V) enabled in BIOS — required for emulator acceleration.
OS
Windows 10 v1903+ or Windows 11 — WSL2 recommended for Docker tasks later. 64-bit required.
Key Windows Configurations
Enable Developer Mode in Settings → Update & Security → For Developers
Enable Hyper-V or Virtualization in BIOS (required for Android emulator HAXM)
Disable Windows Defender real-time scanning on node_modules folders (speeds up npm installs)
Set Windows PATH length to allow Long Paths via Group Policy or registry
Install Windows Terminal (modern tabbed terminal for running multiple shells)
Install PowerShell 7+ and configure execution policy with Set-ExecutionPolicy RemoteSigned
⚠
Common Mistake: Skipping BIOS virtualization enables Intel HAXM fails silently and Android emulator runs at 5 FPS. Always verify virtualization is ON before installing Android Studio.

NPM Concepts You Must Know
npm install — reads package.json and installs all deps into node_modules
npm ci — clean install from package-lock.json, used in CI pipelines for reproducibility
node_modules — never commit this folder. Add to .gitignore always.
package-lock.json — locks exact versions. Always commit this for reproducible builds.
devDependencies — Playwright belongs here, not dependencies, since it's test-only
npx — run a package binary without global install, e.g. npx playwright test

Android Studio, SDK & Emulator Setup

›
What You Need and Why
Android Studio
The IDE that bundles the entire Android toolchain — SDK Manager, AVD Manager, and the emulator. Even if you won't write Android code, you need its tools for APK inspection and ADB.
Android SDK
The collection of Android platform tools, build tools, and system images. The SDK is what ADB and emulators use to communicate with devices. You need SDK 29+ (Android 10+).
AVD Manager
Android Virtual Device manager — creates and manages emulator instances. For automation you'll primarily use Appetize cloud, but local emulators are needed for locator discovery.
HAXM / Hypervisor
Hardware Accelerated Execution Manager — uses CPU virtualization to run emulators at near-native speed. Without it, emulators crawl. Install via SDK Manager.
SDK Components to Install
Android SDK Platform 33, 34 (latest two stable versions)
Android SDK Build-Tools 34.0.0
Android SDK Command-line Tools (latest)
Android Emulator
Android SDK Platform-Tools (ADB lives here)
Intel x86 Emulator Accelerator (HAXM) or Android Emulator Hypervisor Driver
Google Play Intel x86_64 Atom System Image (for Play Store apps)
Google USB Driver (for physical device connections)

1.6
ADB — Android Debug Bridge Deep Dive
Device communication, commands, debugging, APK management
›
What ADB Actually Is

ADB is a command-line tool that acts as a bridge between your development machine and an Android device (real or emulated). It uses a client-server architecture: the adb client on your machine communicates with the adb daemon running on the device. Understanding ADB deeply means you can debug any Android issue, install APKs, capture logs, take screenshots, and simulate events — all programmatically.

Essential ADB Commands for Automation Engineers
# Device management
adb devices                           # List all connected devices
adb -s emulator-5554 shell           # Shell into specific device
adb kill-server && adb start-server  # Reset ADB server (fixes 99% of device issues)

# APK operations
adb install TableTennis.apk           # Install app
adb install -r TableTennis.apk        # Reinstall keeping data
adb uninstall com.tabletennis.app     # Uninstall by package name
adb shell pm list packages            # List all installed packages

# UI automation helpers
adb shell uiautomator dump /sdcard/ui.xml  # Dump UI hierarchy to XML
adb pull /sdcard/ui.xml ./ui.xml           # Pull dump to local machine
adb shell screencap /sdcard/screen.png     # Take screenshot
adb pull /sdcard/screen.png ./screen.png   # Pull screenshot

# Logs
adb logcat -v time | grep TableTennis # Filter app logs in real-time
adb logcat -c                          # Clear logcat buffer

# Input simulation
adb shell input tap 500 800           # Tap at coordinates
adb shell input swipe 200 800 200 400 # Swipe up
adb shell input text "Hello"          # Type text
adb shell input keyevent 3            # Press HOME button
APK vs IPA — Understanding Mobile Packages
APK (Android)
Android Package Kit — a ZIP archive containing compiled Java/Kotlin bytecode (classes.dex), resources, manifest, and native libraries. Created by the Android build toolchain. Can be installed via ADB or Appetize upload.
IPA (iOS)
iOS App Store Package — a ZIP archive containing compiled ARM binary, resources, and entitlements. Requires a macOS machine to build and sign. Uploaded to Appetize for cloud iOS testing.

1.7
Appetize Cloud Device Setup
Account creation, APK/IPA upload, session management, API keys
›
What Appetize Is and How It Works

Appetize.io runs real Android and iOS simulators in the cloud, accessible via a browser or programmatic API. For automation, you interact with Appetize through its JavaScript SDK, which streams a virtualized device into a browser page. Playwright then controls the browser page containing the device stream, and Appetize translates Playwright's pointer events into real mobile touch events on the virtualized device. This means no Appium, no device farm setup — just a cloud URL and a session token.

Appetize Setup Steps
1
Create Appetize Account
Go to appetize.io, sign up. Free tier includes 100 minutes/month. Upgrade for CI usage. Note your API token from Dashboard → API.
2
Upload TableTennis APK
Upload via the web dashboard or via API: POST https://api.appetize.io/v1/apps with your APK file and API key. You'll receive a public key for the app.
3
Note the App Public Key
Every uploaded app gets a unique public key (e.g., p7nww3n8e362m3bn). This key is used in your automation config to launch the correct app.
4
Test Device in Browser
Open https://appetize.io/app/{YOUR_KEY} and verify the TableTennis app launches on the cloud device. Interact manually first before automating.
5
Store Credentials in .env
Never hardcode API keys in test code. Store in .env file and access via process.env.APPETIZE_API_KEY.
Uploading APK via API (Node.js)
// scripts/upload-apk.js
const fs = require('fs');
const FormData = require('form-data');
const axios = require('axios');

async function uploadAPK() {
  const form = new FormData();
  form.append('file', fs.createReadStream('./apps/TableTennis.apk'));
  form.append('platform', 'android');

  const response = await axios.post(
    'https://api.appetize.io/v1/apps',
    form,
    {
      headers: {
        ...form.getHeaders(),
        'Authorization': `Bearer ${process.env.APPETIZE_API_KEY}`
      }
    }
  );

  console.log('App Key:', response.data.publicKey);
  // Save this key to your .env as APPETIZE_APP_KEY
}

uploadAPK();

Understanding the Execution Architecture
Test Runner
Playwright Test reads your spec files, creates worker processes, and coordinates parallel execution. Each worker gets its own browser instance.
Browser Context
An isolated browser session — like an incognito window. Each test gets its own context by default, ensuring complete isolation of cookies, storage, and sessions.
Page Object
A single browser tab/window. All automation actions (click, fill, navigate) happen on a page object. You interact with the DOM through a page.
CDP Protocol
Chrome DevTools Protocol — the underlying wire protocol Playwright uses to communicate with Chromium. For WebKit and Firefox, Playwright uses their equivalent protocols.

JavaScript Automation Essentials
Async/await, Promises, classes, modules, error handling
›
Why Async/Await Matters in Automation

Every Playwright interaction — clicking, navigating, waiting — is asynchronous because it involves I/O with a browser process. If you don't await these calls, your code proceeds to the next line before the browser action completes, causing race conditions and flaky tests. Understanding the JS event loop is not academic — it directly determines whether your tests pass reliably.

Async/Await Patterns for Automation
// Pattern 1: Basic async test function
test('login test', async ({ page }) => {
  await page.goto('https://sttc.onrender.com/login');
  await page.fill('#username', 'testuser');
  await page.fill('#password', 'testpass');
  await page.click('button[type="submit"]');
});

// Pattern 2: Parallel execution with Promise.all
// When two independent async actions can run simultaneously
await Promise.all([
  page.waitForNavigation(),  // Wait for nav...
  page.click('#submit')      // ...while clicking
]);

// Pattern 3: Error handling in async tests
test('flaky api check', async ({ page }) => {
  try {
    await page.goto('https://sttc.onrender.com', { timeout: 30000 });
  } catch (err) {
    console.error('Navigation failed:', err.message);
    throw err; // Re-throw so test fails properly
  }
});
JavaScript Fundamentals for Automation
Destructuring — const { page, context } = args — used constantly in Playwright fixtures
Template literals — `Hello ${name}` — used in dynamic selectors and log messages
Arrow functions — () => {} — used in test callbacks, locator filters, and array methods
Spread/Rest — ...options — used in config merging and fixture composition
Optional chaining — user?.profile?.name — safely accessing nested API response fields
Classes — class LoginPage — the foundation of Page Object Model

Array methods — .filter(), .map(), .find() — processing test data sets

2.2
Playwright Locator Strategies
Selector hierarchy, resilient locators, anti-patterns
›
Locator Priority Hierarchy (Best to Worst)
1. Role locators — getByRole('button', {name: 'Login'}) — most resilient, tied to accessibility semantics
2. Label locators — getByLabel('Email address') — targets form inputs by their label text
3. Placeholder — getByPlaceholder('Enter email') — good for inputs without labels
4. Text locators — getByText('Submit') — targets by visible text, fragile if text changes
5. Test IDs — getByTestId('login-btn') — requires devs to add data-testid attributes
6. CSS selectors — locator('#login-btn') — reliable if IDs are stable, fragile otherwise
7. XPath — locator('//button[@id="login"]') — use only as last resort, brittle
AVOID — index-based selectors like nth(2), absolute XPaths, or class-only selectors
Playwright Locator API
// Playwright's locator() is lazy — it doesn't find the element until an action is called
const loginBtn = page.getByRole('button', { name: 'Login' });

// Chaining locators — narrows scope
const form = page.locator('form#login-form');
const emailField = form.getByLabel('Email');

// Filter locators — select from multiple matching elements
const activePlayer = page
  .locator('.player-card')
  .filter({ hasText: 'Ma Long' });

// Counting elements
const count = await page.locator('.player-row').count();
console.log(`Found ${count} players`);

// Getting all matching elements
const players = await page.locator('.player-name').allTextContents();
2.3
Assertions, Waits & Network Interception
Auto-waiting, expect API, request interception, response mocking
›
Playwright Auto-Waiting (Why It's Special)

Unlike older tools that require explicit sleep() calls, Playwright automatically waits for elements to be actionable before interacting. "Actionable" means: visible, stable (not animating), not obscured, enabled, and attached to the DOM. This eliminates 80% of flaky tests caused by race conditions. However, you must still understand timeouts and when auto-waiting is NOT enough.

Core Assertions
// All expect() assertions are async and auto-retry until timeout
await expect(page.locator('#welcome-msg')).toBeVisible();
await expect(page.locator('#score')).toHaveText('11-9');
await expect(page.locator('#submit-btn')).toBeEnabled();
await expect(page.locator('input#email')).toHaveValue('test@test.com');
await expect(page).toHaveURL(/dashboard/);
await expect(page).toHaveTitle('TableTennis Club');

// Soft assertions — don't stop test on failure
await expect.soft(page.locator('#logo')).toBeVisible();
await expect.soft(page.locator('#nav')).toBeVisible();
// All soft assertion failures are collected and reported together
Network Interception
// Intercept and mock API responses for stable testing
await page.route('**/api/players', async route => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',

      { id: 1, name: 'Ma Long', ranking: 1 },
      { id: 2, name: 'Fan Zhendong', ranking: 2 }
    ])

});

// Monitor API calls without mocking
const [response] = await Promise.all([
  page.waitForResponse('**/api/login'),

3.1
Appetize Session Architecture
How Playwright communicates with a cloud mobile device
›
End-to-End Communication Flow
Step 1: Session Init
Your automation opens a Playwright page to the Appetize embed URL with your app public key and device config. Appetize allocates a cloud device and starts the app.
Step 2: WebSocket
Appetize establishes a WebSocket connection streaming the device screen as video frames into the browser viewport. The device is running in a datacenter.
Step 3: Input Mapping
Playwright's pointer events (click, move, touchstart) land on the Appetize canvas element. Appetize translates canvas coordinates to device screen coordinates and sends touch events to the virtual device.
Step 4: SDK Control
Appetize's JavaScript SDK (appetize.io/sdk) provides a higher-level API: session.tap(), session.swipe(), session.typeText() — these are wrappers around the coordinate translation layer.
Setting Up Appetize Session in Playwright
// mobile/helpers/appetize-session.js
const { chromium } = require('@playwright/test');

async function createMobileSession(appKey, device = 'pixel6', os = 'android') {
  const browser = await chromium.launch({ headless: false });
  const context = await browser.newContext();
  const page = await context.newPage();

  const url = `https://appetize.io/embed/${appKey}?device=${device}&os=${os}&autoplay=true`;
  await page.goto(url);

  // Wait for device to finish booting and app to launch
  await page.waitForSelector('.appetize-device-screen', { timeout: 60000 });
  await page.waitForTimeout(5000); // App launch buffer

  return { browser, context, page };
}

module.exports = { createMobileSession };
ℹ
Appetize sessions have a timeout (default 120 seconds of inactivity). In long test suites, send periodic keepalive interactions or configure session.keepAlive = true in the SDK to prevent premature termination.

Touch Gestures & Mobile Interactions
Tap, swipe, long press, scroll, drag, rotation, keyboard
›
Gesture Implementation Patterns
// mobile/utils/gestures.js — Reusable gesture utilities

class MobileGestures {
  constructor(page) {
    this.page = page;
    this.deviceCanvas = page.locator('.appetize-device');
  }

  async tap(x, y) {
    const box = await this.deviceCanvas.boundingBox();
    await this.page.mouse.click(box.x + x, box.y + y);
  }

  async swipeUp(startY = 700, endY = 300, x = 200) {
    const box = await this.deviceCanvas.boundingBox();
    await this.page.mouse.move(box.x + x, box.y + startY);
    await this.page.mouse.down();
    await this.page.mouse.move(box.x + x, box.y + endY, { steps: 20 });
    await this.page.mouse.up();
  }

  async longPress(x, y, durationMs = 1500) {
    const box = await this.deviceCanvas.boundingBox();
    await this.page.mouse.move(box.x + x, box.y + y);
    await this.page.mouse.down();
    await this.page.waitForTimeout(durationMs);
    await this.page.mouse.up();
  }

  async typeText(text) {
    await this.page.keyboard.type(text, { delay: 80 });
  }

  async rotateToLandscape() {
    // Via Appetize SDK API call injected into page
    await this.page.evaluate(() => {
      window.appetize?.session.setOrientation('landscape');
    });
  }
}

module.exports = { MobileGestures };
Mobile Locator Strategies
Accessibility ID — accessibility id=login-button — most stable mobile locator, works across Android & iOS
Resource ID — resource-id=com.tabletennis:id/btn_login — Android-specific, generated from XML layout resource names
Content Description — content-desc=Submit score — Android accessibility attribute set by developers
UIAutomator — new UiSelector().text("Login") — Android-only, powerful for complex element selection
XPath — last resort, use only when accessibility attributes are absent
Image matching — Appetize supports visual element detection for cases where text attributes are unreliable

Page Object Model for Web

What is POM and Why It Exists

Page Object Model is a design pattern where each screen of your application is represented as a JavaScript class. The class contains the locators for that screen and the actions a user performs on it. Tests then use these classes instead of raw selectors. When the UI changes, you update one class — not 50 test files. This is the single most impactful pattern for test maintainability at scale.

LoginPage Implementation
// pages/web/LoginPage.js
class LoginPage {
  constructor(page) {
    this.page = page;

    // Define all locators as class properties
    this.emailInput    = page.getByLabel('Email');
    this.passwordInput = page.getByLabel('Password');
    this.loginButton   = page.getByRole('button', { name: 'Login' });
    this.errorMessage  = page.locator('.error-alert');
    this.forgotLink    = page.getByText('Forgot password?');
  }

  async navigate() {
    await this.page.goto('https://sttc.onrender.com/login');
  }

  async login(email, password) {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(password);
    await this.loginButton.click();
  }

  async getErrorMessage() {
    return this.errorMessage.textContent();
  }

  async verifySuccessfulLogin() {
    await this.page.waitForURL('**/dashboard');
  }
}

module.exports = { LoginPage };

// utils/logger.js — Production-level structured logger
const fs = require('fs');
const path = require('path');

const LEVELS = { DEBUG: 0, INFO: 1, WARN: 2, ERROR: 3 };
const COLORS = {
  DEBUG: '\x1b[36m', INFO: '\x1b[32m',
  WARN:  '\x1b[33m', ERROR: '\x1b[31m'
};

class Logger {
  constructor(context = 'Test') {
    this.context = context;
    this.level = LEVELS[process.env.LOG_LEVEL || 'INFO'];
    this.logFile = path.join('logs', `run-${Date.now()}.log`);
    fs.mkdirSync('logs', { recursive: true });
  }

  _log(level, message, meta = {}) {
    if (LEVELS[level] < this.level) return;
    const ts = new Date().toISOString();
    const entry = { ts, level, context: this.context, message, ...meta };
    const color = COLORS[level];
    console.log(`${color}[${ts}] [${level}] [${this.context}] ${message}\x1b[0m`);
    fs.appendFileSync(this.logFile, JSON.stringify(entry) + '\n');
  }

  debug(msg, meta) { this._log('DEBUG', msg, meta); }
  info(msg, meta)  { this._log('INFO',  msg, meta); }
  warn(msg, meta)  { this._log('WARN',  msg, meta); }
  error(msg, meta) { this._log('ERROR', msg, meta); }
}

module.exports = { Logger };

CI/CD Best Practices
npm ci over npm install — ci uses locked versions, making builds fully reproducible
Cache node_modules — saves 2-3 min per run by caching based on package-lock hash
Retries in CI — set retries: 2 in CI to handle infrastructure flakiness (network blips, slow devices)
Always upload artifacts — use if: always() so reports are saved even on test failure
Matrix builds — test across multiple browsers in parallel using GitHub Actions matrix strategy
PR gates — configure required status checks so PRs cannot merge with failing tests
Sharding — split large test suites across multiple runners: --shard=1/4 pattern
Scheduled smoke tests — run critical path every 30 min against production to catch incidents
