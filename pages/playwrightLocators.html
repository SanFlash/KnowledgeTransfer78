Phase 1 · Fundamentals

Why Playwright Locators?

Playwright ships with a powerful, semantic locator API that makes tests significantly more readable, stable, and aligned with how real users interact with your application. Understanding why this matters is as important as knowing how to use it.

The Goal of Automation: Simulate the User

When a real user fills in a form, they look for the label that says "Email". When they click a button, they read its text — "Submit". They don't look at CSS class names like .btn-primary-v2 or XPath expressions. Playwright's semantic locators reflect this reality.

The Three Pillars of Good Locators

  • Stability — The locator should not break when CSS classes, layout, or non-semantic attributes change.
  • Readability — Any QA engineer reading the test should immediately understand what element is being targeted.
  • Accessibility-aligned — Locators that work with ARIA roles naturally also verify your app is accessible.

How Playwright Executes Locators

Unlike Selenium's findElement, Playwright locators are lazy. They don't query the DOM immediately. They represent a way to find an element, and only when you perform an action (.click(), .fill(), .textContent()) does the actual DOM lookup happen. This enables built-in auto-waiting.

JavaScript
Lazy evaluation — no DOM query yet
// This line does NOT touch the DOM yet
const btn = page.getByRole('button', { name: 'Submit' });

// The DOM is queried HERE, with auto-waiting built in
await btn.click();

// Playwright waits for:
// ✓ Element to appear in DOM
// ✓ Element to be visible
// ✓ Element to be stable (not animating)
// ✓ Element to receive pointer events
// ✓ Element to be enabled

The XPath Problem

XPath was designed for XML querying in the early 2000s. Using it as a UI locator strategy in 2024+ is problematic for many reasons — and Playwright strongly discourages it.

Why XPath Breaks Your Tests

❌ XPath — Fragile
// Breaks if ANY parent changes
const btn = page.locator(
  '/html/body/div[2]/main/section[1]/form/div[3]/button'
);

// Breaks if class changes
const el = page.locator(
  '//div[@class="btn-primary-v2"]'
);

// Impossible to read — what is this?
const el2 = page.locator(
  '(//table//tr)[3]/td[2]'
);
✅ Playwright Native — Stable
// Works regardless of page structure
const btn = page.getByRole(
  'button', { name: 'Sign In' }
);

// Works if class changes; reads like English
const el = page.getByRole(
  'button', { name: 'Submit Order' }
);

// Crystal clear — row 3, "Price" column
const el2 = page
  .getByRole('row', { name: 'Product A' })
  .getByRole('cell', { name: 'Price' });

XPath vs. Playwright Native — Comparison

DimensionXPathPlaywright Native

Accessibility alignmentNoneBuilt-in
Auto-wait supportPartialFull

Maintenance costHighLow
⚠️
XPath Use Cases That Still Apply

XPath is acceptable for: traversing upward in the DOM (e.g., finding a parent element), querying text using contains() in legacy tools, or targeting elements that have no other stable identifier AND you've exhausted all other options. In Playwright, even these cases usually have a better solution through chaining and filtering.

Priority Order — Which to Reach For First

  1. getByRole() — If the element has a semantic HTML role (button, link, checkbox, textbox…), this is always first choice.

  2. getByLabel() — For form inputs that have an associated label. Covers 90%+ of form fields.

  3. getByPlaceholder() — When a label doesn't exist but the input has a placeholder.

  5. getByTestId() — When devs have added data-testid attributes. Best agreed upon as a team practice.

  6. locator() with CSS — Last resort for elements without any other stable identifier. Prefer over XPath.

Phase 2 · Core Locators

getByRole() — The Gold Standard

getByRole() is Playwright's most powerful locator. It uses the W3C Accessible Rich Internet Applications (ARIA) spec — the same system screen readers use — to find elements. This means your tests simultaneously verify accessibility.

Syntax

JavaScript
page.getByRole(role, options)

// Options:
{
  name: 'string or regex',     // accessible name (text / aria-label)
  exact: true | false,         // exact match on name (default: false)
  checked: true | false,       // for checkboxes/radios
  disabled: true | false,      // filter by disabled state
  expanded: true | false,      // for expandable elements
  pressed: true | false,       // for toggle buttons
  selected: true | false,      // for options in listbox
  level: 1-6,                   // for headings
  includeHidden: false,        // include hidden elements
}

Practical Examples

Example 1: Buttons

JavaScript
Button locators
// HTML: <button type="submit">Submit Order</button>
await page.getByRole('button', { name: 'Submit Order' }).click();

// HTML: <button aria-label="Close dialog">✕</button>
await page.getByRole('button', { name: 'Close dialog' }).click();

// Case-insensitive partial match
await page.getByRole('button', { name: /submit/i }).click();

// Exact match to avoid matching "Submit Order" and "Submit Draft"
await page.getByRole('button', { name: 'Submit', exact: true }).click();

// Disabled button assertion
await expect(
  page.getByRole('button', { name: 'Submit', disabled: true })
).toBeVisible();

Example 2: Navigation Links

JavaScript
// HTML: <nav><a href="/about">About Us</a></nav>
await page.getByRole('link', { name: 'About Us' }).click();

// Scope to navigation to avoid matching page body links
await page
  .getByRole('navigation')
  .getByRole('link', { name: 'Products' })
  .click();

Example 3: Checkboxes & Radios

JavaScript
// HTML: <label><input type="checkbox"> Remember me</label>
await page.getByRole('checkbox', { name: 'Remember me' }).check();

// Assert it's checked
await expect(
  page.getByRole('checkbox', { name: 'Remember me' })
).toBeChecked();

// Radio buttons
await page.getByRole('radio', { name: 'Annual billing' }).check();
await page.getByRole('radio', { name: 'Monthly billing' }).check();

Example 4: Headings

JavaScript
// Assert page title is correct
await expect(
  page.getByRole('heading', { name: 'Your Dashboard', level: 1 })
).toBeVisible();

// Section heading (h2)
await expect(
  page.getByRole('heading', { name: 'Recent Orders', level: 2 })
).toBeVisible();

getByText() — Visible Text Locator

Finds elements by their visible text content. Best for non-interactive elements like paragraphs, labels, menu items, and status messages — not for buttons or inputs (use getByRole for those).

Syntax & Options

JavaScript
page.getByText(text, options)
// text: string or RegExp
// options: { exact: boolean } — default: false (substring match)

Example 1: Status messages & alerts

JavaScript
// HTML: <p class="alert-success">Your order has been placed.</p>
await expect(
  page.getByText('Your order has been placed.')
).toBeVisible();

// Partial match (default) — finds "Your order has been placed. Thank you!"
await expect(
  page.getByText('Your order has been placed')
).toBeVisible();

// Regex — flexible matching
await expect(
  page.getByText(/order.*placed/i)
).toBeVisible();

// Exact match — avoids matching similar text
await expect(
  page.getByText('Saved', { exact: true })
).toBeVisible();

Example 2: Menu items and list items

JavaScript
// HTML: <ul><li>Electronics</li><li>Clothing</li></ul>
await page.getByText('Electronics').click();

// Scoped to a specific list to avoid ambiguity
await page
  .getByRole('list')
  .getByText('Electronics')
  .click();
⚠️
Important: getByText() Matches Parent Containers

getByText('Hello') may match a <div> that contains a <p>Hello</p>. Always use exact: true or scope with a parent locator when targeting specific elements.

getByLabel() — Form Fields by Label

Finds form elements (inputs, textareas, selects) by the text of their associated <label>. This is the preferred way to target form fields because it reflects exactly how users identify them.

How Label Association Works

HTML
Three ways to associate a label
<!-- Method 1: for/id pairing (most common) -->
<label for="username">Username</label>
<input id="username" type="text">

<!-- Method 2: wrapping (implicit association) -->
<label>
  Password
  <input type="password">
</label>

<!-- Method 3: aria-labelledby -->
<span id="search-label">Search</span>
<input aria-labelledby="search-label" type="search">
JavaScript
getByLabel() examples
// Works for all three label association methods above
await page.getByLabel('Username').fill('john_doe');
await page.getByLabel('Password').fill('S3cur3P@ss');
await page.getByLabel('Search').fill('laptop');

// Select dropdowns
await page.getByLabel('Country').selectOption('India');

// Textarea
await page.getByLabel('Comments').fill('Great product!');

// Partial label match (default)
await page.getByLabel('Email').fill('user@example.com');
// Matches: "Email Address", "Email *", "Email (required)"

// Exact match
await page.getByLabel('Email', { exact: true }).fill('user@example.com');
// Only matches: "Email" (not "Email Address")

getByPlaceholder() — Input Placeholder Text

A fallback locator for inputs that lack a <label>. Prefer getByLabel() when possible, since placeholder text is often not accessible to screen readers.

JavaScript
// HTML: <input type="email" placeholder="Enter your email address">
await page.getByPlaceholder('Enter your email address').fill('test@test.com');

// Partial match
await page.getByPlaceholder('email').fill('test@test.com');

// Regex
await page.getByPlaceholder(/search/i).fill('playwright');
💡
When to Use getByPlaceholder()

Use this when the input has no label AND adding a label is not immediately possible. It's also useful for search bars that often rely on placeholder text as their visible indicator.

getByTestId() — Test-Specific Attributes

Uses a dedicated test attribute (default: data-testid) to locate elements. Highly stable since these attributes exist purely for testing and won't change with UI redesigns. Requires a team agreement to add them consistently.

Setup: Configuring Custom Test ID Attribute

JavaScript
playwright.config.js
import { defineConfig } from '@playwright/test';

export default defineConfig({
  use: {
    // Default is 'data-testid', change as needed
    testIdAttribute: 'data-testid',
    // Or use custom: 'data-qa', 'data-cy', 'data-test'
    testIdAttribute: 'data-qa',
  }
});
JavaScript
Usage
// HTML: <div data-testid="shopping-cart">3 items</div>
const cart = page.getByTestId('shopping-cart');
await expect(cart).toContainText('3 items');

// HTML: <button data-testid="add-to-cart-btn">Add to Cart</button>
await page.getByTestId('add-to-cart-btn').click();

// Combine: find within a scoped area
const productCard = page.getByTestId('product-card-42');
await productCard.getByRole('button', { name: 'Add to Cart' }).click();

locator() — CSS Selectors

The generic locator() method accepts CSS selectors (and XPath as a last resort). Use CSS selectors when you need to scope by attributes, pseudo-classes, or structural selectors not covered by semantic methods.

JavaScript
CSS selector examples
// By ID (stable but IDs can be auto-generated — verify first)
page.locator('#submit-btn');

// By attribute value
page.locator('[data-product-id="42"]');

// By input type
page.locator('input[type="file"]');

// nth-of-type (use .nth() method instead when possible)
page.locator('li:nth-of-type(2)');

// Combining attributes
page.locator('input[type="text"][name="city"]');

// Has pseudo-class (Playwright extension)
// Finds .card that CONTAINS a .badge with text "Sale"
page.locator('.card').filter({ hasText: 'Sale' });

// ✋ XPath — use only when absolutely necessary
page.locator('xpath=//div[@aria-label="Filter panel"]');

Phase 3 · Advanced Techniques

Chaining & Scoping Locators

Chaining is one of Playwright's most powerful features. You start with a container locator and then use locator methods on it. This scopes all subsequent queries to elements within that container.

JavaScript
Scoping pattern
// PATTERN: parent.child()
const dialog = page.getByRole('dialog', { name: 'Confirm Delete' });
await dialog.getByRole('button', { name: 'Yes, Delete' }).click();
// Much safer than: page.getByRole('button', { name: 'Yes, Delete' })
// which might match other buttons on the page.

// ─────────────────────────────────────────────
// Real-world: Shopping cart item
const cartSection = page.getByTestId('cart-panel');
const laptopItem = cartSection
  .getByRole('listitem')
  .filter({ hasText: 'Gaming Laptop' });

await laptopItem.getByRole('button', { name: 'Remove' }).click();

// ─────────────────────────────────────────────
// Navigation menu scoping
const nav = page.getByRole('navigation', { name: 'Main navigation' });
await nav.getByRole('link', { name: 'Settings' }).click();

The has Option — Filter by Child Element

JavaScript
// Find a row that contains a specific cell value
const row = page
  .getByRole('row')
  .filter({
    has: page.getByRole('cell', { name: 'John Doe' })
  });

// Click the Edit button in that specific row
await row.getByRole('button', { name: 'Edit' }).click();

// Find card that has BOTH a heading AND a price badge
const premiumCard = page
  .locator('.product-card')
  .filter({ hasText: 'Premium' })
  .filter({
    has: page.locator('.badge-sale')
  });

Filters, nth(), first(), last()

When multiple elements match a locator, you need tools to narrow the selection. Playwright provides .filter(), .nth(), .first(), and .last() for this purpose.

JavaScript
Narrowing multiple matches
// ── .first() and .last() ──
const firstProduct = page.getByRole('listitem').first();
const lastProduct  = page.getByRole('listitem').last();

await expect(firstProduct).toContainText('Gaming Laptop');

// ── .nth(index) — zero-based ──
const secondRow = page.getByRole('row').nth(1); // index 0 = first

// ── .filter({ hasText }) ──
const saleItems = page
  .getByRole('listitem')
  .filter({ hasText: 'SALE' });

const count = await saleItems.count();
console.log(`Found ${count} items on sale`);

// ── .filter({ hasNot }) — negative filter ──
const inStockItems = page
  .getByRole('listitem')
  .filter({ hasNotText: 'Out of Stock' });

// ── Combining filters ──
const target = page
  .getByRole('row')
  .filter({ hasText: 'Active' })      // has status "Active"
  .filter({ hasText: 'Admin' })        // AND has role "Admin"
  .first();                              // take the first match

Counting & Iterating

JavaScript
// Count elements
const items = page.getByRole('listitem');
await expect(items).toHaveCount(5);

// Iterate over all matching elements
const allItems = await page.getByRole('listitem').all();
for (const item of allItems) {
  const text = await item.textContent();
  console.log(text);
}

// Assert all items contain a common word
await expect(page.getByRole('listitem'))
  .toContainText(['Item 1', 'Item 2', 'Item 3']);

Dynamic Elements

Dynamic elements appear and disappear based on user actions, API responses, or timers. Playwright's auto-waiting handles most cases, but here are advanced patterns for tricky scenarios.

JavaScript
Waiting patterns
// ── Wait for element to appear ──
await expect(
  page.getByRole('alert')
).toBeVisible({ timeout: 10000 });

// ── Wait for element to disappear ──
await expect(
  page.getByTestId('loading-spinner')
).toBeHidden();

// ── Wait for text to change ──
await expect(
  page.getByTestId('status-badge')
).toHaveText('Processing');

// ── Elements in a dynamically-loaded list ──
// After clicking "Load more", wait for new items
const initialCount = await page.getByRole('listitem').count();
await page.getByRole('button', { name: 'Load more' }).click();
await expect(page.getByRole('listitem'))
  .toHaveCount(initialCount + 10);

// ── Locating items in a select populated via API ──
await page.getByLabel('Country').click();
await expect(
  page.getByRole('option', { name: 'India' })
).toBeVisible();
await page.getByRole('option', { name: 'India' }).click();

Strict Mode — Handling Multiple Matches

Playwright is in "strict mode" for actions like .click() and .fill(). If your locator matches more than one element, it throws a "strict mode violation" error. This is a safety net — not a bug.

🚫
Strict Mode Violation Error

Error: locator.click: Error: strict mode violation: getByRole('button', { name: 'Edit' }) resolved to 5 elements

JavaScript
Resolving strict mode violations
// ❌ PROBLEM: Multiple "Edit" buttons
await page.getByRole('button', { name: 'Edit' }).click(); // Throws!

// ✅ SOLUTION 1: Scope to a specific row
const johnRow = page
  .getByRole('row')
  .filter({ hasText: 'John Doe' });
await johnRow.getByRole('button', { name: 'Edit' }).click();

// ✅ SOLUTION 2: Use .nth()
await page.getByRole('button', { name: 'Edit' }).nth(0).click();
// Use only if order is guaranteed and meaningful

// ✅ SOLUTION 3: Add aria-label to distinguish
// Ask devs to add: aria-label="Edit John Doe"
await page.getByRole('button', { name: 'Edit John Doe' }).click();

// ── Checking count before acting ──
const editBtns = page.getByRole('button', { name: 'Edit' });
await expect(editBtns).toHaveCount(3); // Assert expected count
await editBtns.nth(0).click();         // Safe now

  2. A product listing has multiple "Add to Cart" buttons. Write a locator that adds the cheapest item (the one with text "$9.99") to the cart.

Phase 4 · Real-world Scenarios

Form Handling

Forms are the most common UI element in web apps. Here's a complete, production-grade approach to handling all form element types.

Complete Registration Form

JavaScript
Full form interaction
async function fillRegistrationForm(page, data) {
  // ── Text inputs ──
  await page.getByLabel('First Name').fill(data.firstName);
  await page.getByLabel('Last Name').fill(data.lastName);
  await page.getByLabel('Email Address').fill(data.email);
  await page.getByLabel('Password').fill(data.password);

  // ── Native select dropdown ──
  await page.getByLabel('Country').selectOption(data.country);
  // Or by value: .selectOption({ value: 'IN' })
  // Or by index: .selectOption({ index: 2 })

  // ── Radio buttons ──
  await page
    .getByRole('radio', { name: data.accountType })
    .check();

  // ── Checkboxes ──
  if (data.agreeToTerms) {
    await page
      .getByRole('checkbox', { name: 'I agree to the Terms' })
      .check();
  }

  // ── File upload ──
  if (data.avatar) {
    await page.getByLabel('Profile Picture')
      .setInputFiles(data.avatar);
  }

  // ── Textarea ──
  await page.getByLabel('Bio').fill(data.bio);

  // ── Custom combobox / autocomplete ──
  await page.getByRole('combobox', { name: 'Skills' }).click();
  await page.getByRole('option', { name: 'JavaScript' }).click();

  // ── Submit ──
  await page.getByRole('button', { name: 'Create Account' }).click();
}

// ── Form Validation Assertions ──
async function assertFormErrors(page) {
  // Error next to a field
  const emailGroup = page.locator('.form-group')
    .filter({ has: page.getByLabel('Email') });
  await expect(
    emailGroup.getByRole('alert')
  ).toContainText('Invalid email');

  // Field marked as invalid (aria-invalid)
  await expect(
    page.getByLabel('Email')
  ).toHaveAttribute('aria-invalid', 'true');
}

Tables & Lists

Tables and lists are the most challenging elements to write stable locators for. Here are proven patterns.

JavaScript
Table locator patterns
// ── Assert cell value in a specific row ──
const table = page.getByRole('table');

const johnRow = table
  .getByRole('row')
  .filter({ hasText: 'John Doe' });

// Get a specific cell by column header context
// Pattern: find row → find cell by its approximate position
await expect(
  johnRow.getByRole('cell').nth(2)  // 3rd cell = "Status"
).toContainText('Active');

// ── More robust: get column index first ──
const headers = table.getByRole('columnheader');
const headerTexts = await headers.allTextContents();
const statusCol = headerTexts.indexOf('Status');

await expect(
  johnRow.getByRole('cell').nth(statusCol)
).toContainText('Active');

// ── Click action button in a table row ──
await table
  .getByRole('row')
  .filter({ hasText: 'Jane Smith' })
  .getByRole('button', { name: 'Delete' })
  .click();

// ── Verify full table row contents ──
const firstDataRow = table
  .getByRole('row')
  .nth(1); // Skip header row (index 0)

await expect(firstDataRow).toContainText([

Phase 6 · Mastery

Best Practices

These are the habits and patterns that separate good automation from great automation. Build these into your muscle memory.

1. Always Prefer Semantic Locators

❌ Avoid
// Fragile — breaks on any refactor
page.locator('.btn.btn-primary.submit-btn');
page.locator('#formContainer > div:nth-child(3) > input');
page.locator('//button[@class="btn btn-primary"]');
✅ Prefer
// Stable — aligned with user intent
page.getByRole('button', { name: 'Submit' });
page.getByLabel('Email Address');
page.getByRole('button', { name: 'Submit' });

2. Use Page Object Model (POM)

JavaScript
pages/LoginPage.js
export class LoginPage {
  constructor(page) {
    this.page = page;

    // Define locators ONCE — reuse everywhere
    this.emailInput    = page.getByLabel('Email');
    this.passwordInput = page.getByLabel('Password');
    this.submitButton  = page.getByRole('button', { name: 'Sign In' });
    this.errorMessage  = page.getByRole('alert');
  }

  async goto() {
    await this.page.goto('/login');
  }

  async login(email, password) {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(password);
    await this.submitButton.click();
  }

  async assertError(message) {
    await expect(this.errorMessage).toContainText(message);
  }
}

3. Work With Developers on test-id Strategy

💡
Team Best Practice

Agree on a data-testid naming convention with your dev team. Suggested format: [component]-[element]-[context]. Examples: product-card-title, checkout-submit-btn, user-table-row. These should be added during development, not retrofitted.

4. Never Hard-code Timeouts

❌ Anti-pattern
// Hard-coded waits are flaky
await page.waitForTimeout(3000);
await page.getByText('Success').click();
✅ Best Practice
// Use expect with auto-waiting
await expect(
  page.getByText('Success')
).toBeVisible();

5. Scope Locators to Avoid Ambiguity

JavaScript
// ❌ Page-global — which "Submit" button?
await page.getByRole('button', { name: 'Submit' }).click();

// ✅ Scoped — unambiguous
const form = page.getByRole('form', { name: 'Registration' });
await form.getByRole('button', { name: 'Submit' }).click();

6. Use Regex for Dynamic Text

JavaScript
// ❌ Exact match breaks for dynamic order numbers
await expect(page.getByText('Order #ORD-2024-00042')).toBeVisible();

// ✅ Regex handles dynamic values
await expect(page.getByText(/Order #ORD-\d+/)).toBeVisible();

// ✅ Also for welcome messages with dynamic usernames
await expect(page.getByText(/Welcome,\s+\w+/)).toBeVisible();

Anti-patterns to Avoid

These are the most common mistakes QA engineers make when writing Playwright tests. Learn to recognize and avoid them.

❌ Anti-pattern #1

CSS Classes as Locators

// Breaks on refactor / rebrand
page.locator('.btn-primary-v2')
page.locator('.MuiButton-root')
✅ Fix

Use semantic role + accessible name

// Stable across redesigns
page.getByRole('button', {
  name: 'Place Order'
})
❌ Anti-pattern #2

Auto-generated IDs

// Random IDs change every build
page.locator('#ember-123')
page.locator('#react-select-3-input')
✅ Fix

Ask devs to add stable data-testid

// Or use label/role instead
page.getByTestId('city-select')
page.getByLabel('City')
❌ Anti-pattern #3

Deep XPath Chains

// Breaks on any DOM change
'//body/div[1]/main/section/form/div[3]/button'
✅ Fix

Scope from nearest stable parent

// Structural changes don't matter
page
  .getByRole('form')
  .getByRole('button', { name: 'Submit' })
❌ Anti-pattern #4

waitForTimeout for loading

// Slow AND unreliable
await page.waitForTimeout(5000);
await btn.click();
✅ Fix

Wait for a specific condition

// Fast AND deterministic
await expect(spinner).toBeHidden();
await btn.click();

Quick Reference: What to Use vs Avoid

Scenario❌ Avoid✅ Use Instead
Click a buttonCSS class, XPathgetByRole('button', {name})
Fill a form fieldID, name attributegetByLabel()
Assert visible textgetByText() on interactive elementsgetByText() / toContainText()
Navigate linksPage-global locatorScope to nav → getByRole('link')
Multiple same elements.first() blindly.filter() then .nth()
Wait for state changewaitForTimeout()expect().toBeVisible() / toBeHidden()
Dynamic contentExact string matchRegex: /pattern/
